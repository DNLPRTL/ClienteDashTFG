## Method family

- Family: imitation learning / behavior cloning / quality-aware ABR / lifelong learning.
- Client-side / server-side / hybrid: trained model used by client/player; training/outer loop can be server-side.
- Learning type: policy imitates an expert strategy generated by an instant solver / virtual player.
- Relation to ABR: directly trains an ABR policy to choose future chunk bitrate/quality.

## State / action / reward

### State

Comyco groups input state into three blocks:

- network features: measured throughput for past chunks;
- video content features: next chunk size per bitrate and perceptual video quality per bitrate;
- playback features: previous perceptual quality, buffer occupancy history, download time history and normalized chunks remaining.

For DashClientModular4, the useful subset is: throughput/download history, buffer, last representation/quality, chunks remaining if available, and next chunk sizes only if available without leakage. VMAF/perceptual quality is deferred in Phase 3.5 and must not be forced as a runtime dependency.

### Action

Discrete action space: softmax over bitrate/representation levels. The paper's example uses 6 output probabilities. DashClientModular4 must map this to valid `representation_index` values from the MPD.

### Reward / QoE

Comyco uses a video-quality-aware QoE formulation based on perceptual quality/VMAF plus rebuffering and smoothness terms. For this TFG, Phase 3.5 has already fixed `qoe_linear_v1` and `reward_n`; Comyco does not override that reward.

## Model and training

- Architecture: 1D-CNN feature extraction for network/content/playback inputs; GRU layer; softmax output.
- Training method: imitation learning with expert action labels; cross-entropy-style behavior cloning loss plus entropy regularization; experience replay.
- Expert / teacher: instant solver using a virtual player and horizon-based QoE maximization with future throughput known during expert generation.
- Online interaction: optional lifelong/outer loop, not adopted in Phase 4 base.
- Offline data: network traces + video dataset.
- Fine-tuning: lifelong update mechanism exists but is too ambitious for base TFG implementation.
- Compute requirements: reports major sample/training efficiency gains; default multi-agent training uses 12 agents matching CPU cores of their PC.

## Data and evaluation

- Datasets / traces: Kwai traces, Waterloo/SQoE-style quality data and DASH video quality dataset described in paper.
- Train split: trace/video sampling during training.
- Validation split: not reused directly.
- Test split: trace-driven and real-world experiments.
- OOD split: limited compared with later MetaABR/SABR/BETA literature.
- Baselines: Pensieve, RobustMPC, Oboe and other model-based/learning-based ABR schemes.
- Evaluation type: trace-driven and real-world experiments.
- Real-world evidence: present, but not enough to claim our TFG real-world validation.

## Relevance to DashClientModular4

### What this source justifies

- Imitation learning is a strong CPU-first candidate because it avoids expensive RL exploration.
- Expert labels can be generated offline using MPC/RobustMPC/oracle-like strategies.
- Cross-entropy over discrete representation labels is a simple and defensible training objective.
- A model can be small and still scientifically meaningful.
- Teacher labels may use future information, but only labels may use it; model inputs must not.

### What this source does NOT justify

- It does not justify forcing VMAF into Phase 4 runtime, because VMAF is deferred in DashClientModular4.
- It does not justify training from dry-runs legacy.
- It does not justify lifelong learning as base implementation.
- It does not justify leaking future throughput or future chunk quality into model inputs.

### Risks for this TFG

- Leakage risk: high if the instant solver/oracle future information contaminates model inputs.
- Future-information risk: BLOCK unless explicitly separated as teacher-only information.
- Reward hacking risk: medium; expert objective must match `reward_n` contract.
- Overfitting risk: medium/high without trace-regime balancing.
- Hardware risk: low/medium for small behavior cloning; high for full lifelong multi-agent reproduction.
- Dependency risk: medium if reproducing original stack; low if designing NeuralABR-Lite from scratch.

## Decision impact

- Method score: very high.
- Feasibility score: high for behavior cloning / policy distillation.
- Defense strength: high.
- Implementation consequence: preferred base hypothesis for NeuralABR-Lite training, with strong leakage safeguards.
